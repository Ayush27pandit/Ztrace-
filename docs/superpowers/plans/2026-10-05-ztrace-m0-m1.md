# Ztrace M0 + M1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Scaffold the Ztrace TypeScript monorepo and stand up a durable job foundation: Postgres/Prisma investigation state, Redis/BullMQ queue, worker with leases/recovery, health endpoints, and tests proving idempotent state transitions.

**Architecture:** Two apps (api, worker) sharing a `src/` core. PostgreSQL is the source of truth for investigation state; BullMQ on Redis is only the execution mechanism. All external adapters (Jira, GitHub, observability, LLM) are left as interfaces — not implemented in this plan.

**Tech Stack:** TypeScript, Node.js 22 LTS, Express, Prisma + PostgreSQL (Neon), BullMQ + ioredis (Upstash Redis TLS), pino logging, zod for config validation, vitest for tests, Docker Compose for local dev.

## Global Constraints

- `RCA_MODE=shadow` and `RCA_PUBLISH_TO_JIRA=false` are defaults; publication code stays disabled.
- No secrets in committed files; `.env.example` with blank values only.
- GitHub access read-only (not exercised yet); no repository code execution.
- Atlas adapter disabled until verified; no production database connection.
- Queue payload carries IDs only (`RCAJobPayload`), never ticket/evidence content.
- Audit metadata never stores tokens or secrets.
- Every state transition validated in code; DB transaction where possible.
- Health endpoints must not leak config/secrets/dependency errors.

```ts
import { z } from "zod";

const schema = z.object({
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().min(1),
  RCA_MODE: z.enum(["shadow", "active"]).default("shadow"),
  RCA_PUBLISH_TO_JIRA: z
    .enum(["true", "false"])
    .default("false")
    .transform((v) => v === "true"),
  PORT: z.coerce.number().default(3000),
  LOG_LEVEL: z.string().default("info"),
});

export type Env = z.infer<typeof schema>;
export function parseEnv(e: NodeJS.ProcessEnv): Env {
  return schema.parse(e);
}
```

- [ ] **Step 3: Implement** — transition map covering the happy path and side states (`FAILED`, `CANCELLED`, `REVIEW_REQUIRED` reachable from any non-terminal state; `RUNNING` may go to `RETRY_WAIT`, `FAILED`, `CANCELLED`).

```ts
const transitions: Record<string, string[]> = {
  RECEIVED: ["QUEUED", "CANCELLED", "FAILED"],
  QUEUED: ["RUNNING", "CANCELLED", "FAILED"],
  RUNNING: ["COLLECTING_EVIDENCE", "FAILED", "CANCELLED", "RETRY_WAIT"],
  COLLECTING_EVIDENCE: ["ANALYZING", "FAILED", "CANCELLED", "RETRY_WAIT"],
  ANALYZING: ["VALIDATING", "FAILED", "CANCELLED", "RETRY_WAIT"],
  VALIDATING: ["REPORT_READY", "INSUFFICIENT_EVIDENCE", "FAILED", "RETRY_WAIT"],
  REPORT_READY: ["PUBLISHED", "REVIEW_REQUIRED", "FAILED"],
  PUBLISHED: [],
  INSUFFICIENT_EVIDENCE: ["REVIEW_REQUIRED", "CANCELLED"],
  REVIEW_REQUIRED: [],
  RETRY_WAIT: ["QUEUED", "FAILED", "CANCELLED"],
  FAILED: ["QUEUED", "CANCELLED"],
  CANCELLED: [],
};
export function canTransition(from: string, to: string): boolean {
  return transitions[from]?.includes(to) ?? false;
}
export function assertTransition(from: string, to: string): void {
  if (!canTransition(from, to)) throw new Error(`Invalid transition ${from} -> ${to}`);
}
```
